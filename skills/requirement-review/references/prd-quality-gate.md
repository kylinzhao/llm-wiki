# PRD 质量门禁

用于在 16 维度评审前检查需求文档自身是否达到可评审、可研发评审、可测试和可上线验证的最低要求。来源规范参考 Cwiki 页面 `AI提效 - 出海产品需求文档审核规范`（pageId `670136018`）；使用时只引用需求内容本身，不在输出中暴露本地缓存路径。

## 输出规则

- 在正式报告中先输出“PRD 质量门禁”结论，再进入 16 维度详情。
- 不把所有门禁缺失都升级为阻塞。只有影响唯一实现、验收或上线风险判断的问题才列为 P0/P1。
- 若需求文档是早期草稿，仍执行门禁检查，但把结论表述为“进入研发评审前需补齐”。

## 1. 文档结构

检查：

- 标题是否描述清楚功能范围，避免只写“二期”“改造”“优化”。
- 标题是否能与项目任务看板或需求管理条目对应。
- 是否有修订记录：修订时间、修订人、修订内容、修订原因。
- 是否有目录，且一二级标题完整，层级不超过三级。
- 正文是否至少覆盖背景分析、需求梳理、业务流程、功能规则、数据/埋点、上线验收。

## 2. 调研证据和目标闭环

检查：

- 是否说明问题范围、需求边界、收益价值、紧急程度。
- “解决什么问题”是否有明确损害或机会成本，而不是只有主观诉求。
- “产生什么价值”是否说明增长、效率、路径缩短、体验改善或风险降低。
- 是否说明业务闭环：从哪里开始、在哪里结束、用什么数据验证。
- 是否提供调研证据：用户访谈、焦点小组、销售现场重现、电话录音、微信会话、App 内反馈、工单、电话回访、问卷、竞品体验、销售/顾问/运营反馈等。

## 3. 生命周期交付物

按需求阶段检查交付物是否齐全；缺失时指出进入下一阶段的风险。

| 阶段 | 应有交付物 |
| --- | --- |
| 需求调研 | 用户访谈报告、市场调研报告、竞品分析报告或等价证据 |
| 需求设计 | 需求文档、业务流程图、原型 |
| 产品评审 | 产品内审修订内容、页面关系图、交互原型 |
| 研发评审 | 设计评审、后端技术方案、测试方案或测试用例；前端技术方案按复杂度判断 |
| 开发测试 | 前端/后端/移动端/测试排期、需求修订记录、历史数据迁移或上线准备方案 |
| 上线验证 | 业务宣导、上线申请、上线后数据验证方案 |

不要把“研发侧不能打回需求”作为通用规则；需求 review 仍应指出会阻塞唯一实现或验收的问题。

## 4. 用例化需求

检查：

- 用户原始需求是否映射为系统需求或用例。
- 用例是否描述事件流、前置条件、后置条件。
- 是否定义业务规则、数据规则和非功能约束。
- 是否避免只从“系统要有哪些功能”出发罗列功能清单，而缺少用户、角色、场景和业务意图。

## 5. 业务流程图质量

检查：

- 是否有分角色泳道图；时序强的流程是否在泳道图中标注时序。
- 如单独提供时序图，是否与泳道图对应。
- 是否说明接收哪些信息、产生哪些数据、数据传输路线、由哪些部门/岗位负责。
- 是否列举完整功能入口集，并标注入口入参、出参。

## 6. 名词和实体定义

检查：

- 是否区分业务名词和系统专有名词。
- 专有名词、业务步骤是否解释清楚。
- 特定业务对象是否给出实体定义、关联关系、唯一性或主键、业务语义。
- 新概念是否与现有系统概念冲突。

## 7. 字段、状态和断点

检查：

- 表单必填字段是否说明信息来源：手工录入、系统自动关联、第三方系统、内部系统、广告平台回传、线下表格/单据等。
- 线下表格或单据来源是否说明字段位置、是否非空必填。
- 字段或状态发生增加、删除、调整时，是否说明影响范围，包括通知、其他对象、其他字段、历史数据和权限。
- 有配置状态组合时，是否穷举状态组合对应事件。
- 是否标明系统操作中所有可能断点页面：无权限、详情页对象缺失、提交校验失败、数据不存在、状态不可操作、网络或服务异常等。

## 8. 数据、埋点和统计

检查：

- 前端埋点事件需求和后端数据统计需求是否成对出现。
- 前端埋点是否提供 sample；后端数据落表字段是否提供 sample。
- 指标计算口径是否能支撑上线后效果验证。
- 上线后是否定义 3-7 天内的数据对比报告、对比基线、目标值、观测窗口和责任人。

## 9. 配置、权限、消息和上线

检查：

- 有状态配置的项目是否提供状态机图或文字状态机。
- 权限项是否列全，每个角色默认是否选中。
- 消息通知是否说明触发条件、用户/管理员开关、汇总发送策略、消息文本、消息组件、是否可在消息上处理、点击落地页及多端差异。
- 新老版本、存量数据、灰度、回滚、业务宣导和未达预期处理策略是否明确。
