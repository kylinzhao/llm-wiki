# 设计交付物分层要求（前端评审引用）

本文档与 `FE_REQ_REVIEW_SKILL.md` 配套使用。产品随 PRD 提供的设计依据须**按系统类型**满足下列分层；评审时与 `references/fe-req-signal-noise.md` §2.3「现网依据」一并检查。

---

## 一、交付物类型

| 类型 | 含义 |
|------|------|
| 低保真原型 | 线框、流程示意、可点击低保真稿，用于说明布局与主路径 |
| 高保真原型 | 接近终稿视觉与交互的可点击原型，仍非研发切图依据 |
| 设计稿 | 设计团队输出的高保真正式稿（含关键状态与标注），作为 ToC 默认交付标准 |

PRD 须**显式标注**本需求采用的交付物类型，并提供**可访问链接**（或附件路径）；不得仅用文字描述替代。

---

## 二、按系统类型的最低要求

### §2.1 ToC 系统（面向终端用户）

**范围示例**：车主 App/小程序/H5、车商端、投放落地页等直接面向 C 端或业务一线用户的界面。

**要求**：必须提供**设计稿**。低保真或高保真原型**不能**单独作为设计交付物。

**缺失**：无设计稿链接/附件，或仅提供低保真/高保真原型 → 记 `前端完整性` 或 `信息结构`（违反 **§2.1**），建议默认 **P1**（团队可对高风险 ToC 升 **P0**）。

### §2.2 中台 / 后台系统

**范围示例**：运营后台、BD 工作台、检测/评估管理后台、商立方后台等内部作业与配置系统。

**要求**：可接受**低保真原型**或**高保真原型**作为设计交付物；若已有正式**设计稿**，应在 PRD 中一并给出。交付物类型须在 PRD 中写清。

**缺失**：无任何原型或设计稿依据，且 UI 有新增或变更 → 记 `前端完整性`（违反 **§2.2**），建议 **P1**。

---

## 三、与需求分档的关系

- **轻量改动**（纯文案、样式微调且无结构变化）：若可完全对照现网设计稿 diff，可注明「无新设计交付物，沿用现网设计稿 xxx」。
- **标准档及以上**（新页面、新弹层、交互变更）：须满足本节 §2.1 或 §2.2。
- 系统类型不明时，评审 finding 中列为**待产品确认**，并按 **ToC 标准**从严建议补设计稿。

---

## 四、输出要求

在 `FE_REQ_REVIEW_SKILL.md` 按页评审前或「零、信息结构与噪声」之后，若涉及 UI 变更，须说明：

- 系统类型（ToC / 中台后台）
- 实际提供的交付物类型与链接
- 是否满足 §2.1 或 §2.2

不满足时写入 `问题与缺失` 表或信息结构 finding，**归属区域**示例：`主页面-全局` / `交付物-设计依据`。
