# 需求文档：有效信息、噪声与信息结构（前端评审引用）

本文档与 `FE_REQ_REVIEW_SKILL.md` 配套使用。**不推断文档由人还是 AI 撰写**；仅依据可观察结构与文本特征给出 finding。

审查时先完成本节检查，再进入该 skill 的「按页面维度」交互/状态/埋点诊断。

---

## 一、Finding 类型

| 类型代码 | 含义 |
|----------|------|
| `信息结构` | 有效信息未凸显、范围不可界定、无法映射到按页评审 |
| `噪声` | 篇幅与信息密度不匹配、套话簇、重复定义 |
| `前端完整性` | 沿用 `FE_REQ_REVIEW_SKILL.md` 各页下的状态/交互/边界/埋点 |

每条 finding 须包含：**类型**、**违反条款**（本节条款编号）、**证据**（标题或小节名 + 摘录）、**要求补什么**（一句话）、**是否阻塞开发**（由团队档位策略定；本节默认见 §四）。

---

## 二、有效信息未凸显（结构规则，§2.1–§2.3）

在**第一个实质「需求详情 / 具体规则 / 功能说明」类主章节之前**（若文档无此类章节则全文视为未满足 §2.1），逐项检查以下三项。**不**因「文风像 AI」单独判负。

### §2.1 可交付变更摘要

**判定**：存在等价内容块，且块内为**有限条**（建议 ≤10 条）bullet 或编号列表，且每条能对应至少一类可验收对象：**页面或主入口、字段/控件、接口行为、状态迁移**之一。

等价标题示例（命中其一即可）：`本需求变更点`、`迭代说明`、`变更摘要`、`需求变更`、`diff`。

**缺失**：无任何等价块，或仅有背景/价值/目标而无上述列表 → 记 `信息结构`，违反 **§2.1**。

### §2.2 范围边界

**判定**：至少满足其一：

- **适用**：明确写出承载能力的页面/系统名、菜单或路由级入口；或
- **非目标**：明确写出本迭代**不做**的范围（可与「适用」同段）。

**缺失**：二者皆无 → 记 `信息结构`，违反 **§2.2**。

### §2.3 现网依据

**判定**：至少具备其一（可组合）：现网/上一版 **Cwiki 或 PRD 链接**、**原型/设计稿链接**、**关键界面截图**（带页面语境）。

**缺失**：全文无任何可跳转依据，且具体规则无法与现网对齐 → 记 `信息结构`，违反 **§2.3**。

### §2.4 组合触发（信号弱）

- **缺失 §2.1、§2.2、§2.3 中任意 2 项** → 必须产出一条总述 finding：**有效信息未凸显**（`信息结构`），证据中列出缺失条款编号。
- **三项均缺失** → 同上，且建议在 finding 中标注 **强信号**（仍由团队决定是否阻塞）。

### §2.5 与按页评审的映射

若 §2.1–§2.3 已部分满足，但「具体规则」段落**无法归入** `FE_REQ_REVIEW_SKILL.md` 所定义的任一主页面及其附属弹层 → 记 `信息结构`，违反 **§2.5**，要求产品将规则归位到「页面 / 区域」后再做前端完整性评审。

## 三、噪声过大（启发式，§3.1–§3.4）

以下各项为**弱规则**，**不得单独**作为「不符合规范」的唯一依据；至少 **命中下列子条款中的 2 条** 才记一条 **`噪声`** finding。

### §3.1 头重脚轻

**度量**（实现时二选一，在 skill 内写死一种）：

- **按段落**：从文档开头到「第一个含具体实体的规则段落」之间，若「背景 / 价值 / 目标 / 行业分析 / 综述」类小节段落数 ≥ 其余含实体规则段落的段落数，或
- **按字数**：上述「泛章节」累计字数 > 全文 **25%**（不含代码块与表格内纯数字列）。

**实体**指：字段名、按钮或链文案、Tab/步骤名、明确页面或模块名、接口名、**明确状态枚举值**（如未修改/已修改）等。

### §3.2 套话簇

在同一段或相邻两段内，出现 **≥3 次** 无验收点的泛化表述，且其间**无**带实体的新增规则。可用于弱匹配的示例短语（可扩展列表）：`提升满意度`、`规范流程`、`可追溯`、`提高效率`、`赋能`、`闭环`、`优化体验`、`保障数据一致性`（单独出现且无配套数据规则时不算实体）。

### §3.3 表格灌水

表格中存在多行：删掉该行后**无法判断**实现是否变化，且该行**不指代**任何字段/按钮/页面区域（即无实体词、也不引用前文已定义实体）→ 计 1 次命中；同表累计 ≥2 行则 §3.3 成立。

### §3.4 重复定义

**任一**：两个同名或实质重复的一级标题；同一规则在「详情表」与「交互说明」中**纯复述**且无新增条件（若字句高度重合 >70% 由评审员/模型判断）。

## 四、默认等级与阻塞策略（可与团队档位表叠加）

| 触发 | 建议默认等级 | 默认是否阻塞开发 |
|------|----------------|------------------|
| §2.4 缺失任意 2 项 | P1（档位要求严时可升 P0） | 由团队定 |
| §2.4 三项均缺 | P0 或 P1 | 建议阻塞至补全摘要+范围+依据 |
| 仅 §3 命中（噪声） | P2；若同时 §2 已严重缺失则 P1 | **不**单独因噪声阻塞 |
| §2.5 无法映射到页面 | P1 | 建议阻塞至归位后再做页面级评审 |

团队若采用「软约束 + 评审清单」，可将上表「建议阻塞」落实为前端评审 comment 中的 **阻塞项**，与 JIRA 流程对齐。

## 五、输出要求（写入主 skill 输出时）

在按页输出 `FE_REQ_REVIEW_SKILL.md` 规定结构**之前**，增加一节（标题自定，例如「零、信息结构与噪声」）：

- 列出本节产生的 **§二、§三** finding（无则写「未发现信息结构/噪声类问题」）。
- 每条遵循 **§一** 的 finding 字段。

随后再进入各页面的「问题与缺失」「埋点建议」。
